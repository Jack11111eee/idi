## 二、问题清单

**1|P2|§8.2 循环链:核查→修复跳无触发物(前轮漏检,v1.10 补丁不对称暴露)**
- 位置:§8.2「每轮循环 = 两个独立调用……的链」段;对照 §7.3②、§8.2「继续修复」定义。
- 描述:全文其他推进节点均有钉死触发物(G1 按钮、「处理本轮批注」、「继续撰写」、档位弹选触发首轮核查、v1.10 新补的"修复完后端自动开下一轮核查"),唯独"核查报告落盘(FIX/BLOCK)→修复调用启动"这一跳无任何显式定义:「继续修复」字面定义为裁决落盘后的**重跑**("续跑以含问题与裁决的报告为磁盘输入"),暂停期外是否呈现未说;「继续自检」被限定为中断恢复且重跑的是**核查**轮(§7.3②);"链""含**刚落盘**的核查报告"只是隐含。check-10 P2-3 的判据("各步显式触发,此处无入口→停摆")原样适用于此跳;v1.10 给反向跳补了自动句,恰恰使这一跳的留白从"全链皆隐含"变为"一跳明一跳暗"。两读(整体自动流水线/停在核查后等待)导出不同实现,后者即循环停摆。
- 建议修法:补一句"核查报告落盘且末行非 PASS 时,由后端自动启动修复调用"(与已补的反向跳同构、同款)。

**2|P2|§6.4 裁决追加文法:多组裁决共存时幂等与"对应"配对无文法**
- 位置:§6.4「后端仅当标记不存在时追加(幂等)」「存在 `> 待裁决:` 行且无对应 `> 裁决:` 行」;§8.2 判暂停态条款。
- 描述:同轮报告二次抛问是可达场景(报告含多个用户职权类问题,如范围/非目标;修复续跑处理问题 2、3 时再遇问题 3)。此时报告尾部已有 `> 待裁决:A` + `> 裁决:A`:①"仅当标记不存在时追加"按字面(同类标记已存在)使第二个 `> 待裁决:` 无法落盘——新问题无磁盘签名,违 §7.2 文件即状态;②暂停态判定"存在待裁决行**且无对应**裁决行"因旧对已配对而误判为非暂停,「继续自检」不隐藏,误点即重跑覆盖当轮报告,**第一问的裁决与新问题一并销毁**——恰是 v1.8~v1.10 三轮反复封堵的事故;③"对应"如何建立(内容一致?行序配对?序号?)无关法,两组共存即无法机械判定。善意读法(按所追加条目的内容判重)虽存在,但"不存在"的宾语粒度两个实现者会取不同答案。
- 建议修法:幂等改为"仅当**该问题**尚无 `> 待裁决:` 行时追加"(内容级判重);配对钉死序号文法(如 `> 待裁决:#1:…` / `> 裁决:#1:…`,同号即对应)。

**3|P2|§8.2 "修复正常完成"无机械判定协议——抛问识别自 v1.8 起为空白,自动推进使其后果升级**
- 位置:§8.2「严格档每轮修复**正常完成**后,由后端自动开启下一轮核查」+「修复者必须停下来在界面抛出问题」。
- 描述:自动推进要求后端区分修复调用的三种结束:正常完成(自动开下一轮)/抛问暂停(截存、落盘 `> 待裁决:`、隐藏「继续自检」)/意外中断(「继续自检」恢复)。后两者对后端是同一次调用的不同出口,分界完全依赖后端"截存"修复者抛出的问题——而"停下来在界面抛出问题"这一事件在调用输出/事件流中无任何识别文法(什么形态算抛问?最后一条消息?独立标记事件?),自 v1.8 引入截存以来即靠实现者自行发明。此前该空白只影响展示(用户在场手动驱动);v1.10 自动化后,识别失败即被当作"正常完成",后端直接开下一轮核查:用户职权类问题被绕过、待裁决落盘与按钮分流整套机制空转,违背"获用户裁决后才继续"的既有规定。
- 建议修法:一句级钉死契约:修复者以固定格式的独立消息抛问(如以 `> 待裁决:` 前缀的事件行),后端以该标记截存并转入暂停——自动推进仅在"调用正常结束且全程无该标记"时触发。

另查两处未计问题,沿用先例放行:「§7.3② "未完成修复项在**下一轮**核查报告重现"与"重跑**当前**核查轮"的编号松动(check-7 已判措辞级,操作性规则已钉死编号行为);宽松档零问题轮由核查执行者写 PASS、常态由修复者收尾,两句并存无行为分歧。
