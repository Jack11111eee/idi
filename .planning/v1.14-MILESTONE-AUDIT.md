## 5. Broken E2E flow — the one blocking finding

> **CLOSED 2026-09-25 by quick `260925-iin` (FIX 1 + FIX 2).** The regression below was real and is now fixed; the gate that failed to catch it now catches it. `frontend/app.js:253` reads `item.scrollIntoView({ block: 'nearest' })` (following the outer `#main-pane`, so L-4 is not rolled back), and `check-05 --item 9` gained an auto-follow assertion placed **before** the first `_idi06_reach()` call — the latter sets `c.scrollTop = scrollHeight` itself, so placing it after would have been vacuously green. The gate is mutation-proven: neutralizing `scrollIntoView` yields `item 9: FAIL (17 条断言, 1 FAIL, 0 BLOCKED)`, exit 1, with `after=0 last=[2569,2621] pane=[0,900]`. `idi-06`'s re-verification (2026-09-25) records this as a now-closed side effect of its L-4 change. The section is retained verbatim below as the finding of record.

### AI 事件直播 no longer auto-follows the newest event

**The link that broke:** Phase 6's L-4 scroll-container convergence (`6adcaa3`, idi-06-02, 2026-09-22) deleted `max-height: 55vh` and `overflow-y: auto` from `.event-list` **in place**. `.event-list` is `#ai-events` (`index.html:76`, bound at `app.js:5`). With no `overflow` declaration it computes `overflow-y: visible` — it is no longer a scroll container, so `app.js:253`'s `eventsEl.scrollTop = eventsEl.scrollHeight; // 保持最新可见` is a **no-op by CSS spec**: `scrollTop` is always 0 on a non-scrollable element.

**Nothing replaced it.** The only other `scrollTop` writers in `app.js` are lines 270/293/299, all on `chatMessages` — a different element. Nothing scrolls `#main-pane`, the outer scroller that L-4 promoted. The commit's own comment states the intent — 「条目随外层 `#main-pane` 滚动」 — but no code makes the outer pane follow.

**This is a regression introduced by this milestone, not a pre-existing condition.** At base `0c658aa` the rule carried `max-height: 55vh; overflow-y: auto`, so auto-follow worked. Confirmed by `git show 0c658aa:frontend/style.css` against `6adcaa3`'s diff.

**Gate coverage is zero — and worse than zero.** check-05 `--item 9` *affirmatively asserts the regression's precondition*:

```
PASS [p1] #ai-events 计算 max-height == none: expected=none actual=none  # L-4:套娃第一层(55vh 限高 + 内滚动)已原地删除
PASS [p1] 面板区滚动者集合 == {#main-pane, #chat-messages, #latest-check}: …  # 口径取「恰好」而非「至多」
```

Its only scroll-behaviour assertion is 「末条内容可达」, which **sets** `c.scrollTop = scrollHeight` itself (`check-05-ui-uat.py:2483`) before reading rects. That is *reachability under an explicit scroll* — a different property from *auto-follow*. A green item 9 therefore cannot detect this break, and the scroller census is pinned to exactly the set that has no auto-follow. This is the third instance in this milestone of the same pattern: a gate whose label reads as covering a behaviour it does not measure (item 8's 768px branch and item 9's judged set were the first two, both since corrected).

**User-visible impact:** during a multi-minute AI call, new events append below the fold and the panel never follows; the user must scroll the main pane by hand. The SSE path is an unconditional `renderEvent` (`app.js:192-197`), so this affects the core 「看 AI 干活」 flow in phases 1-2 and 3.

**No requirement is unmet as written.** LAYOUT-04's text is 「侧栏滚动容器套娃收敛」 — the convergence happened. The regression is an uncovered *side effect* of achieving it. So this is **not** a requirements-coverage gap; it is an integration/flow gap. It is nonetheless blocking for the audit because `flows` is one of the four scored dimensions and this flow is broken with zero coverage.

**Fix shape:** small. Either make the outer pane follow (`mainPane.scrollTop = mainPane.scrollHeight` alongside `app.js:253`, or a `scrollIntoView` on the appended item), or restore the inner scroller. The first preserves L-4's intent; note that changing `frontend/app.js` or `frontend/style.css` will invalidate Phase 8's (or Phase 6/7's) fingerprint and require the corresponding re-verify.
