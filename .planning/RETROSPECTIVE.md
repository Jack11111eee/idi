## Milestone: v1.13 — 交互式讨论迭代系统 MVP

**Shipped:** 2026-09-13
**Phases:** 3 | **Plans:** 13 | **Tasks:** 28

### What Was Built

- **行走骨架(Phase 1)**:FastAPI 服务器 + 单界面;双轨 AICaller(SDK / `claude -p --output-format stream-json`)界面契约一致;SSE 事件直播(说/读/写/命令/结果/错误/完成七种 kind)+ 中止;`derive_state()` §7.4 八行推导表(文件即状态);阶段 1-2 连续会话与 transcript 恢复;发散模式;G1 定稿为 `discuss-round-1.md`。
- **轮次收敛循环(Phase 2)**:划词批注与大白话即时答双轨;批注回应表回写 `answer`/`status`(AI 不碰 JSON);轮次冻结只读;`grammar.py` §6.4 六条文法解析器 + 正反例测试矩阵。
- **授权、自检与终点(Phase 3)**:G3 四处机械校验 + 确认词 + 后端写 `AUTHORIZATION.md`;`DESIGN.md.tmp` 原子落盘;宽松/严格两档自检、核查者/修复者双角色自动循环;D-22 残余裁决制(纯 P2 轮转用户逐条裁决);崩溃自愈;使命完成只读归档。

**规模:** 155 commits,2026-09-08 → 2026-09-13;13,322 LOC(不含 vendor);15 个测试文件,219 passed / 6 skipped(慢速真 CLI E2E 由 `IDI_E2E=1` 门控)。

### What Worked

- **纵向 MVP 切阶段**:P1 骨架 → P2 收敛循环 → P3 门与终点,每阶段结束都能用真实目录跑通一段端到端流程,验证永远有真实对象可用。
- **真浏览器 UAT(原始 CDP)**:三个阶段的 UAT 共抓出 6 处机器级验证与静态读码都漏掉的真实缺陷,包括一处高危的无界自动链(实测 84 跳/1.5s)。这是本项目最有性价比的验证手段。
- **验证器 + 缺口修复 + 原验证器复验的闭环**:`gaps_found` → 独立复现确认 → 修复分支 → 原验证器复验 → 翻状态,三次(Phase 1/2/3)全部一次收敛。
- **指纹漂移的诚实处理**:Phase 1 与里程碑收口的 Phase 1/2 `covered_digest` 漂移,一律以重新验证刷新指纹收口,而非覆盖状态字段。

### What Was Inefficient

- **plan-checker 三轮迭代**:Phase 3 计划经 3 轮才通过(3B+5W+2I → 1B+3W+1I → PASS),其中多条(如 `AuthorizeBody` 空体 422 陷阱、路由交付权归属)本可在计划阶段一次说清。
- **STATE.md 在 `phase.complete` 后出现字段异常**(`completed_phases: 1`、By-Phase 表重复、进度条 0%),需人工修正——工具侧的状态写入与派生视图未完全对齐。
- **CLI 耗尽窗口**:真实 CLI 调用偶发停滞 20+ 分钟零事件,只能中止重试,期间无法区分"慢"与"死"。
- **用户全局 `settings.json` 的 allow 规则**一度绕过 §5.4 权限门,直到实测才暴露——环境依赖类风险靠读码发现不了。

### Patterns Established

- **两路线必须 `setting_sources=[]`(SDK)/`--setting-sources=`(CLI)**:屏蔽全局 allow 规则,权限矩阵才成立。
- **AI 不写结构化文件**:annotations 字段、`AUTHORIZATION.md`、`DESIGN.md` 改名全由后端执行,AI 只产出内容,格式漂移归零。
- **纯模块 + 薄路由**:`grammar.py`/`annotations.py`/`g3.py`/`checks.py` 无 I/O 依赖、可独立测;路由只做接线与 409 分流。
- **锁定模块的增量演进**:Phase 3 新增解析器只在 `grammar.py` 文件末尾追加,Phase 2 的六个解析器与 `_VERDICT_RE` 字节不变。
- **缺口修复只碰必要文件**:G-idi03-1~4 全部修复仅 3 个文件(session.py/app.js/测试),grammar/state/checks/g3/main/prompts 零改动。

### Key Lessons

1. **门通过 ≠ 语义成立。** D-P3-16 的决策覆盖 gate 报 30/30(它只扫 PLAN/SUMMARY 文本),而同一条决策在运行时是活偏差(G-idi03-1 无界自动链)。任何"文本级 gate"必须配行为验证佐证。
2. **文件即状态的推论要推到边界。** "冻结 = 纯磁盘推导(轮号 < current_round)"和"半成品报告重跑覆盖"这类推论,一旦落到实现就省掉整个状态机——但推论必须在计划期显式写出,否则实现者会各自发明。
3. **锚点与配对空间必须单一口径。** 裁决行的"结论行取末一处"锚点若与展示层的扫描口径不一致(G-idi03-2),界面就会静默隐藏用户必须看到的问题。
4. **预算纪律前置**:单跳调用必须有明确的 hop 上界,否则 `finally` 守卫写反就是无界循环。
5. **Prompt 契约要测**:"函数接受了参数"不等于"参数进了 prompt"(`build_check_prompt` 的 tier 注入缺陷靠真 E2E 才抓到)。

### Cost Observations

- Model mix: 编排器与执行器以 sonnet 为主,验证/审计类子代理用 sonnet 或 opus(按任务深度)
- Sessions: 跨多个会话,期间遭遇 503/429/ENOTFOUND 与 600s 流看门狗停滞,均以恢复或重启代理收敛
- Notable: 真 CLI E2E 是耗时大头(单次真实调用数分钟起),但正是它抓到了 prompt 注入缺陷;慢速测试用 `IDI_E2E=1` 门控,日常套件保持秒级

## Milestone: v1.14 — 前端视觉与可访问性

**Shipped:** 2026-09-26(范围收口 2026-09-24,归档 2026-09-26)
**Phases:** 6 | **Plans:** 21 | **Tasks:** 60

### What Was Built

- **设计契约与令牌层(Phase 4 + 4.1)**:`style.css` 顶部单一围栏 `:root` 令牌块(8 档字号 / 5 条行高 / 4 个 `z-index` / 25 个 Radix primitive / 47 个 `--color-*`),全部字面量替换为 `var()`,围栏外裸 hex 由 117 归 0;四条零依赖契约校验命令(`check-01`…`check-04`),每条失败方向经变异证明。颜色族由手调 hex 换成 Radix Colors 12 步语义刻度。
- **排版与视觉层级(Phase 5)**:不可逆的 G3 授权按钮在**形态**上与五只例行/承诺按钮分离(淡底 vs 实心 vs 实心更深,四个强调通道用满);页面级层级链 28 > 24 > 22 > 14 由运行时断言钉死;`renderMarkdown()` 全部 9 个注入目标的标题刻度受控(UA 默认与第四字重档 700 退出应用);侧栏活动面板由纯 CSS 推导标出;两处写死 emoji 换成跟随令牌的掩码字形。

- **交互状态与焦点(Phase 7)**:全站作者化 `:focus-visible`(七选择器 + 三条 PAIR)、hover/active/disabled 三态覆盖(禁用态**未被软化**)、过渡限定两个属性 120ms + `prefers-reduced-motion`。
- **可访问性语义与键盘(Phase 8)**:`#round-doc` 的 Tab 停靠点让 Phase 7 预埋的焦点环第一次真正生效;Shift 释放手势把键盘文本选区接成可用的批注路径;两个阻塞弹窗宣告 `role="dialog"` + `aria-modal` 并由原生 `inert` 让该宣告成真,单点 Escape 分派器;`b9664e0` 五条修复的六项人工验收全量重跑。
- **收口期(quick `260925-iin` + 预收口审计)**:修复一处跨阶段回归,新增两条门,处置 backlog `999.1` 的两项,并让六个阶段的指纹全部重新验证通过。

**规模:** 296 commits,2026-09-17 → 2026-09-26;产品面 23 文件 +8490 / −401;前端 3,831 LOC(`style.css` 1708 / `app.js` 1854 / `index.html` 269);后端零改动(219 passed / 6 skipped)。

### What Worked

- **预收口审计真的抓到了东西。** `/gsd-audit-milestone` 的跨阶段集成检查发现 Phase 6 的 L-4 静默杀掉了 AI 事件自动跟随——这是一个**零覆盖**的真实回归,而且没有任何单阶段验证会看到它(它跨两个阶段:改 CSS 的阶段与写 `scrollTop` 的阶段)。里程碑收口前的这次独立审计是本里程碑性价比最高的一步。
- **变异测试作为门的验收标准。** 本里程碑反复出现「门绿但没在看」的缺陷,而**唯一**能证明一条门真的会失败的手段是把被测行为破坏掉、看它变红。FIX 2 的自动跟随门与 FIX 5 的枚举对齐门都按这个标准交付,并留下了逐字的变异输出。
- **「先怀疑自己的探针」。** 两次假警报(把 999.2 的前提误判为陈旧、把 SUMMARY 的 `status` 误判为缺失)都由逐字复测原命令澄清,而不是靠推理。第二次尤其:差一点就让一条真实缺口被「订正」掉。
- **用户裁定与执行分离。** 20px 字面量的处置(加档 / 重映射 / 加例外)是一个真正的排版决策,不是机械替换——把它交回用户、并锁定修法形状后再执行,避免了执行器自行发明第三种修法。
- **指纹作废的诚实处理。** 本次修复让 6 个阶段的指纹全部失效。处置是**逐份以 HEAD 内容重新验证**,而不是刷新旧指纹——刷新等于断言「自验证以来什么都没变」,而这里恰好是假的。

### What Was Inefficient

- **`check-05 --item 9` 的存在本身就是一次浪费。** 它不但没覆盖自动跟随,还正面断言了回归的前提(`#ai-events 计算 max-height == none`)。一条断言了错误不变量的门比没有门更糟:它会让后来者以为这块已被守住。教训是「门要断言**性质**,不是断言**当前实现的形态**」。
- **`covered_files` 的记账语义没有早点想清。** `REQUIREMENTS.md` 出现在全部 6 份报告里,而 `phase.complete` 每次收口都会改它——收口动作本身会打掉所有报告。这个问题在 Phase 4 就被记下并建议移出,直到收口前才真正执行。**下游记账文件不该进 `covered_files`。**
- **`phase.complete` 的进度计数器第四次复现异常**(`completed_phases` / `percent` 被往回改)。已注册的 tech-debt,不自愈,每次收口都要编排器自己核盘。
- **门标签宽于实测四处。** L-5「每个」实为 9/10 行、L-6 只测可见行、SC4 用固定 12 次 Tab 窗口、`check-07` g1 措辞不符。都不影响已通过的结论,但门文本与真实覆盖面不一致。
- **plan-checker 抓到了编排器自己引入的矛盾。** Task 4 的反对空转前提「恰好 7 项」与 `<done>` 的「变异 B → FAIL」互斥。这次是好的低效。

### Patterns Established

- **一条门必须能失败,并且要用变异证明。** 交付门时附上「把被测行为破坏掉后它变红」的逐字输出,否则该门视为未交付。
- **门断言性质,不断言实现形态。** 「自动跟随」的性质是「新条目落在可视盒内且**门自己不动滚动位置**」;写成「`max-height == none`」就变成了对当前实现的快照,实现一改门就撒谎。
- **枚举式规则的两侧必须逐字同集,并在两侧都写明。** `FOCUSABLE_SELECTOR`(门)与 `:focus-visible` 的七选择器(CSS)必须同一次改完;只改一侧会让「规则覆盖了谁」与「门检查了谁」重新分叉,而门会绿。
- **反事实探针与常驻门分工。** 门承担可重复的算术断言;探针承担「这条断言有没有服务对象、它的算术在真实渲染值上成不成立」。
- **追加,不重排。** `style.css` 至少一对等特异性规则由源码顺序决定;重排即渲染变更而 diff 看起来完全无辜。本里程碑全程守住。
- **指纹失效后重新验证,不刷新。** 内容真变 → 重新验证;记账性编辑 → 重算指纹并在报告内披露改了什么。判据是拿 HEAD 内容重算比对,不是看 mtime。

### Key Lessons

1. **单阶段验证看不到跨阶段回归。** L-4 的改动在 Phase 6 完全正确(它的门全绿),`scrollTop` 的代码在 Phase 2 完全正确;错的是两者的**组合**。收口前的独立集成审计是唯一能看见它的位置。
2. **不能失败的门比没有门更糟。** 它不只是漏掉缺陷,还会让缺陷**看起来已被守住**。任何新门都必须先回答「我把它防的那个行为破坏掉,它会红吗」。
3. **下游记账文件不该进 `covered_files`。** 覆盖清单的语义是「其变更足以使本报告结论失效的输入」;需求索引表、状态归一这类每次收口都会变的记账文件不满足该语义,收进去就会让收口动作自我打脸。
4. **子代理的自述不可信,要复测原命令。** 两次假警报都源于「读到了输出,但没读它**怎么产生**的」——item 9 输出里的 `<summary>` 是它自己造的,`SUMMARY.md` 的 `status` 在第 114 行而我只看了前 60 行。
5. **加档优于重映射,当交付物的视觉是已签核的。** 20px → `--text-lg-plus` 保持字形渲染尺寸不变;重映射会改已出货的 ▾/▸ 视觉,加例外则让裸字面量永久留在出货 chrome 里。代价是命名阶梯非单调(xl=24 > 2xl=22),已作为 D-07 冲突登记。

### Cost Observations

- Model mix: 编排器与执行器以 sonnet 为主;验证/审计类子代理用 sonnet 或 opus(按任务深度)
- Sessions: 跨多个会话;本里程碑末期遭遇一次上下文压缩,收口在压缩后继续
- Notable: 真浏览器 UAT(`check-05` 十项 + 两个一次性探针)是耗时大头,但也是唯一能抓到运行时语义缺陷的手段;`check-05` 全量跑 exit=2 是 item 5 两条 `--ai-smoke` 腿按设计 BLOCKED,不是回归

## Milestone: v1.15 — 视觉构图升级

**Shipped:** 2026-09-28(归档 2026-09-28)
**Phases:** 2 | **Plans:** 7 | **Tasks:** 20

### What Was Built

- **卡片容器化与页面底色下沉(Phase 9)**:左栏 4 个面板与右栏 `#doc-panel` 从「完全透明 / 比页面更暗的 gray-2」变为同族白卡片(白底 + 1px 既有容器边界 + 10px 既有圆角 + 零位移极轻阴影);页面底色从 gray-1(`#fcfcfc`,全场最亮)下沉到 gray-3(`#f0f0f0`),使三档刻度 `gray-3 页面 < gray-2 内陷面 < 白卡片` 由真实浏览器读数证明严格递增。页面换值作废的 8 条对比度配对逐条以 HEAD 内容重算登记,其中 2 条按**元素实际绘制面**重新归属到卡片底色(4.77 / 3.32)。
- **表格重做与圆角刻度收敛(Phase 10)**:文档表格由「每格 1px 全边框的电子表格式网格」改为「gray-2 表头浅底 + 仅横向分隔线」;圆角刻度由 `8 / 10 / 28 / 999` 收敛为 `8 / 10 / 999`,两处消费者按各自真实形态就地改归属(`.chat-user` → 卡片档 10px、`#chat-input-row input` → 胶囊档 999px)。两项均零新增颜色值、零新增 primitive、零阈值放宽、零新增 `!important`。
- **两条新运行时门 + 一个探针**:`check-09-idi09-validation.py`(卡片语言 / 页面刻度 / 滚动契约)、`check-10-idi10-validation.py`(表格 / 圆角,99 条断言)、`probe-card-border-token.py`。`check-05-ui-uat.py` 只改 10 行(`.hint` 期望侧重新登记)。
- **连带指纹收口**:实测落定真实形状是「10 份覆盖 `frontend/style.css`,1 份可执行」;唯一可执行的 `idi-09` 以 HEAD 内容**重新验证**而非刷新指纹,`status` 由 `stale` 回到 `passed`。

**规模:** 61 commits,2026-09-26 → 2026-09-27;产品面 5 文件 +1713 / −31;前端 4,035 LOC(`style.css` 1912 / `app.js` 1854 / `index.html` 269);**后端与 `app.js` / `index.html` 逐字节未改**(219 passed / 6 skipped)。

### What Worked

- **用户逐项裁定视觉档位。** 两次范围裁定(「先看看效果吧」→「表格重做, 圆角刻度收敛。做这两个」)与两项档位(表格「表头浅底 + 仅横向分隔」、圆角「严格收敛 8/10/胶囊」)都由用户在 `AskUserQuestion` 中选定。执行器没有自行发明档位——这是本里程碑没有跑偏的主因。
- **「重新归属」是调色与放宽阈值之外的第三种解法。** 页面变暗让**中间调**前景对比度**下降**(与直觉相反),`--color-marker-active` TEXT 重算后 4.18、`--color-border-strong` NON-TEXT 2.91,双双 FAIL。但这两族的元素**全部画在面板内部**,卡片化本身确实改变了它们的绘制面 ⇒ 改记为卡片底色后实测 4.77 / 3.32 双双达标,**零颜色值改动、零 primitive 新增、零阈值放宽**。这不是变通,是如实登记。
- **「零变化」用测量证明,不用算术。** 输入框从 28px 改指胶囊档,判据不是「28px 会被 UA 钳成 26px」这条推断,而是收敛**前后**的真实读数并排:整份 computed style dump 键级 diff + `getBoundingClientRect()` 逐值 + 元素级 PNG **逐字节相同**(两份 PNG sha256 均为 `190d7d7d…`),两份 JSON 的 `style_css_sha256` 不同即「两次真实读数」的凭据。
- **影响面枚举的自我纠错。** 连带指纹面初稿写「6 份」,规划期逐份读盘发现**漏了两个目录**(`v1.13-phases/` 与 `quick/`)⇒ 实为 10 份;再逐份测「路径是否还在盘上」⇒ 只有 1 份可执行。两个方向的错(以为 6 份、以为 10 份都算债务)都被实测挡住。
- **后置代码评审抓到的缺陷被真正修掉。** CR-01 发现 `check-10` 的令牌断言在令牌被删时会经 `ok()` 的 `None` 降级路径记 BLOCKED 而非 FAIL(本项目把 exit 2 当良性码)⇒ `7170fa5` 改判 FAIL 并加令牌存在性硬断言。**这是本项目记录过的同型陷阱第二次出现。**

### What Was Inefficient

- **`check-10` 的判据选窄了,让 G1 活了下来。** 它钉的是**令牌接线**(「`th` 是不是画了 `--color-surface`?」),而里程碑真正需要的是**视觉契约**(「表头读起来是不是一条独立的 band?」)。在 `#latest-check` 这个宿主里答案分别是「是」和「不是」——58/58 PASS 与构图崩塌**共存**。它的抬头逐字记录了创建动机(七个门里零条断言覆盖表格边框/底色),所以这不是疏忽,是**判据粒度**问题。
- **G1 的成因是仓库自己刚修过一次的形态。** `#latest-check` 自身声明 `background: var(--color-surface)` **且自身是 `.markdown-body` 宿主**,Phase 10 用同一令牌画 `th` ⇒ 灰底压灰底。上一阶段刚为 `#doc-panel-header` 修过同形的「同一令牌画在自身底色上」问题(`style.css:802-803`)。**同形缺陷在一个阶段之后被重新造出来** —— 说明上一阶段的修法是**点修**,没有留下可复用的判据。
- **G2:围栏的一条性质被打破,而唯一的门看不见。** `--radix-gray-1` 已声明但全仓库零消费;围栏自己的抬头逐字写着「只声明被消费的令牌」。Phase 10 正是援引这条规则删掉了 `--radius-lg`,却只给它加了一条**专用**的残留断言,没有一般化 ⇒ 下一个 orphan 会再次无声无息。`check-01` 结构上不可能发现它(**它只扫围栏外**)。
- **计划的字面判据本身是错的,记录里留下了一条按字面跑会失败的命令。** `WR-05`:圆角快照 diff 的计划判据写「8 个键」,实测 9 个(第 9 个是被删令牌自身的继承键)。**实质已由测量验证**(矩形相等、元素 PNG 逐字节相同、diff ⊆ 圆角面),错的是计划文本 —— 但归档里那条命令按字面跑会失败。
- **`state.*` 动词第 12–15 次复现。** 四次的形态与第九…十一次逐条一致(`advance-plan` 打坏派生计数、`update-progress` 零写入、`add-decision` 双前缀、`roadmap.update-plan-progress` 两处格式副作用、`mark-complete` 在 `**Coverage:**` 后插空行)。第十五次首次未损坏——因为 `advance-plan` 走了 `last_plan` 的 fail-closed 零写入分支。**核盘仍放在收口序列的最后一个动词之后。**

### Patterns Established

- **门的判据粒度必须写下来:它回答什么、**不**回答什么。** 「令牌接线」与「视觉契约」是两个判据,前者绿不能推出后者绿。新门应在抬头或 SUMMARY 里显式声明它**不**覆盖的那一面(G1 就是这么被发现的)。
- **「零变化」的判据是并排测量,不是算术。** 收敛前后的整份 computed style dump + 矩形逐值 + 元素 PNG 逐字节,三项并排;「X 会被钳成 Y」这类推断不得替代任一项。
- **连带指纹面锚 `covered_files` 逐行匹配,不锚全文 grep。** 全文 grep 会把只在正文提及该文件的报告算进来(实测 `idi-08` frontmatter 命中 0、全文命中 19)。且必须**额外测「路径是否还在盘上」**——只看覆盖名单会把 10 份都算成债务,只看路径解析又会把唯一可执行的那份漏掉。
- **围栏的「每个声明的令牌都被消费」是一条**性质**,需要自己的门。** `check-01` 只扫围栏外,结构上看不见 orphan 的声明。删令牌时顺手加一条**通用**的围栏消费断言,而不是给被删的那个令牌写专用断言。
- **同形缺陷修一次不够,要留下可复用的判据。** G1 是「同一令牌画在自身底色上」的第二次出现(第一次是 `#doc-panel-header`)。点修只解决实例,不解决形态。

### Key Lessons

1. **一条门回答的问题,可能不是它被用来回答的问题。** `check-10` 的 58/58 PASS 与 G1 的构图崩塌完全相容——它从设计上就不回答「表头读起来是不是一条 band」。**新门交付时应显式写下它不覆盖的那一面**,否则下一个人会把「门绿」读成「这块没问题」。
2. **「重新归属」是调色与放宽阈值之外的第三种解法,而且常常是唯一正确的那条。** 当元素的实际绘制面**真的变了**(卡片化把面板内部元素从页面地面搬到了卡片上),重记配对不是变通,是如实登记。判据是「它现在画在什么上」,不是「原来记的是什么」。
3. **影响面枚举要穷尽目录,不能凭印象。** 初稿的「6 份」漏了 `v1.13-phases/` 与 `quick/`——两个都是**归档目录**,而本项目的归档目录正好按里程碑分散在多处。枚举类判据应写成一个能自证覆盖的查询,而不是手列。
4. **计划的字面判据本身可能是错的。** WR-05 的「8 个键 vs 实测 9 个」是计划写错了,不是产品错了。**处置是记录错在哪、由测量承担实质验证**,不是改测量去迎合计划——但归档里会留下一条按字面跑会失败的命令,这一点必须写清楚。
5. **围栏的「无未消费令牌」是性质,`check-01` 是另一回事。** `check-01` 的职责边界是「围栏**外**」;围栏**内**的性质需要围栏自己的门。把「A 门绿」当成「B 性质成立」是同一类错误的又一次实例。

### Cost Observations

- Model mix: 编排器与执行器以 sonnet 为主;验证/审计类子代理用 sonnet 或 opus(按任务深度)
- Sessions: 跨多个会话;本里程碑末期遭遇一次上下文压缩,收口在压缩后继续
- Notable: 本里程碑是**纯 CSS** 的,但耗时大头仍不在写 CSS —— 而在**证明没坏**:五条浏览器门复跑、四个静态门、pytest 基线、以及为「零变化」做的前后并排测量(computed style dump + PNG 逐字节)。`check-05` 全量跑 exit=2 是 item 5 两条 `--ai-smoke` 腿按设计 BLOCKED,不是回归

### What Worked

- **「门必红」被当成证据而不是事故。** 反转后 `check-09` 的 c1..c4 **必然全红** —— 那正是门在正确工作的证据。整个阶段没有一次把它当成需要修的门故障,也没有一次试图用删除断言 / 放宽阈值让红色消失。判据被**改写**为断言新契约,强度只增不减(46 → 102 条)。
- **变异测试是唯一能证明「改写后的门真的会失败」的手段,而本里程碑做了六条。** 逐条给出「变异 → FAIL」的真实读数,并用 `git hash-object frontend/style.css` + `git diff --exit-code` **六次**证明逐字节还原(全程未用 `git stash` —— 它跨工作树共享,本项目明令禁止)。M2 那条尤其有价值:它证明「只钉两侧不同」不够(改指 gray-3 后「两者不同」半条仍 PASS),必须两侧各自钉死。
- **一条会静默死亡的断言被抓住了,而且先复现、再修。** `check-05` 的 `.hint` 背景断言期望侧走运行时解析、因令牌被删返回 `None` ⇒ `ok()` 记 **BLOCKED** 而非 FAIL,而本门退出码本来就因两条 `--ai-smoke` 腿是 **2** ⇒ **门不会变红**。关键在于**先实测复现退化**(`expected=<UNRESOLVED>`,item 5 的 BLOCKED 计数 2 → 3、退出码一动不动)再动手 —— 这条「门绿着在看」的形态是**测出来的**,不是推出来的。
- **编排器的成本理由被磁盘实测推翻,且执行器敢于不服从。** 编排器曾以「改 `check-05` 会作废 7 份覆盖者」为由禁止触碰该文件;实测那 7 份**全部已是 fail-closed stale** ⇒ 边际重验成本为零。执行器按主路线(改期望侧)执行并写明理由。**这是一次正确的抗令**:成本论证的前提被实测证伪时,结论随之失效。
- **「纯 CSS」路线的坚持保住了 `app.js` 逐字节不改。** plan 05 修窗口边缘发丝线时,用户逐项裁定走**纯 CSS 下边线**,而非 JS 加类,也未采用已被验证者否决的 `section.hidden + section:not(.hidden)`(它会同时抹掉 p3 下 `#checks-panel → #ai-panel` 的分隔线)。**取舍是显式的、有记录的,不是默认的。**
- **像素级独立取证给了「人眼半边」一个机器可核的替身。** 5 张截图之外,integration checker 解码 PNG 并扫避开文字的列,逐状态读出「竖线 x=1008 恰 1px」「每状态恰一条横发丝线,落在最后一个可视 section 的下边缘」「p3 / checking / archive 在 y=0 零发丝线」「archive 状态两条线都挺过遮罩」。**「archive 可能破」的怀疑被证伪,而不是被忽略。**

### What Was Inefficient

- **REG-02 的范围被收窄到「点名 `--color-surface-card` 的配对」,于是它守护的散文失真活得比门久。** `style.css:740-742` 的 PAIR 归因散文仍写 `#doc-panel` 声明 `--color-surface`,而 `:907` 实为 `--color-surface-page` ⇒ 它守护的两条 PAIR 登记的地面已不是实际绘制面。**门仍是绿的**(两者在任一面均 ≥ `NON_TEXT_MIN`,仅余量不同:4.48/4.72 与 11.70/12.32)—— 错的是**归属**,而这正是 `REG-02` 被写出来要消灭的那一类缺陷。同型第二处 `:716-717`;`check-05:827` 的诊断串也仍是 Phase 9 的 `5.77`(现为 `5.92`)。**这三处是同一次反转自己造成的**,与 v1.15 被同一批改动推出的那一类同型。
- **门与它守护的清单之间有一层没人守的空隙。** PAIR 的**地面归属**是靠散文描述的,而散文不在任何门的判据里 —— 门只验算术(比值 ≥ 阈值),不验「这条 PAIR 描述的那块面是否还存在」。所以在两个地面同值(都是白)时,比值不变、门全绿,而散文已经失真。**`REG-02` 的措辞(「按元素实际绘制面重新归属」)是对的,但它没有配套一条能自动发现「归属漂移」的判据。**
- **`c2` / `c4` 的断言重叠高估了互异覆盖。** 对 `#doc-panel` 的同样三条断言(左边界宽 1px / == 令牌 / == gray-6 字面量)在 `:368-383`(c2)与 `:476-483`(c4)各写一遍;`#ai-panel` 的零边界同样在 c1 与 c4 重复。非恒真,但**同一条缺陷会在两条路径各报一次** ⇒ c2 19 / c4 39 的计数读起来像 58 条独立覆盖,实际互异覆盖更低。
- **`docstring` / 诊断串的过期是同一种形态,而本里程碑新增了三处。** `check-05` 的 `--item 10` docstring、`check-05:827` 的读数、`check-10:328` 的注释,都是「产品改了、说明没跟上」。它们都不判分,所以没有任何门会红 —— **这正是它们能一直堆积的原因**。
- **`WR-01` 的恒真断言没被顺带修掉。** `check-05:1315-1317` 的 `.hint` 地面断言期望侧与 `<html>` 回退同值 ⇒ 判别力被抹。Phase 11 plan 04 已经把期望侧从 `None` 重新登记到统一面令牌、消除了「`ok()` 期望侧 `None` → BLOCKED」的静默退化,**但恒真性本身仍在**。它超出了本次判据改写的边界,于是留了下来。
- **证据新鲜度:13 份门日志写于 16:19–17:29,而 `frontend/style.css` 于 20:26 被 `707f023` 再改一次**(纯注释文本、零声明改动)。低危且已被独立闭合(integration checker 在 HEAD 上重跑全绿,`idi-12-VERIFICATION.md` 的 verified 时间戳晚于该提交),但**落盘日志确实不覆盖字面最终树**。

### Patterns Established

- **「反转」类里程碑的判据改写三件套:改写 → 变异 → 逐字节还原。** 断言只改写不删除;每条改写后的判据都要有一条「变异 → FAIL」的真实读数;变异在已提交的树上做,定向 `git checkout -- <file>` 还原并证明逐字节相同(**不用 `git stash`**)。没有后两项,「改写」与「放宽」在 diff 上无法区分。
- **断言的数量与方向都要守住。** 断言总数从 46 升到 102 是可核的强度信号;「零条被删除、零条降级为恒真」要逐条对照旧列表,不能靠总数。**判据取真实浏览器 `getComputedStyle` 计算读数**,令牌解析降为 `info()` 诊断。
- **期望侧为 `None` 的断言会静默死亡,而本项目把 exit 2 当良性码。** 任何「期望侧走运行时解析」的断言,在令牌被删/改名时会记 BLOCKED 而非 FAIL;若该门的退出码本来就因别的原因非 0,**它不会变红**。⇒ 令牌解析类断言必须走 `ok_true` 并**显式处理 `None`**(Phase 12 的 `c6` 就是这么写的),或额外加一条令牌存在性硬断言。
- **两级/多级刻度的判据要取「令牌级读数」,不能取 `effective_bg`。** 未被任何元素采用的那一档会被祖先链整个跳过 ⇒ 针对它写的断言在那条不可见的路径上恒真。底色断言应两侧都写死(计算值 == 令牌解析值 **且** == 字面量),以挡住「令牌被改坏而消费者仍接线」时的假绿。
- **装饰性分隔线不登记 NON-TEXT 对比度对。** 发丝线不标识控件或状态 ⇒ SC 1.4.11 不适用。这条依据是逐字引用本文件既有的两处登记,不是本阶段新造的判据。
- **「事实是否被改变」是 stale / 分诊的第一问。** `REG-03` 的 sticky 余量从 `1.000px` 变 `0.000px`,但该断言描述的事实(表头遮挡滚动正文)未被改变 ⇒ **只更新读数与成因登记,判据不动**,且不得把 1px 上边框加回去。反之若事实真变了(内容真变),正确处置是重新验证而非刷新指纹。
- **局部取证产物走专用参数 + 独立子目录。** G1 的局部特写若写进 `--screenshot` 的目录顶层,会让既有的「目录恰含 5 个 PNG」断言变红 —— 而放宽它属仓库明令禁止的「把门改小」。正解是新增 `--g1-snapshot DIR` 参数。
- **fixture 改动要考虑模式不变量。** `checking` fixture 的问题分级表**至少一行 P1**:全 P2 会让 `is_pure_p2` 为真 ⇒ `mode` 翻成 `p2` ⇒ 涟漪波及五条浏览器门与全部截图。且表要紧跟标题行 —— `max-height: 30vh` 使它成滚动区,表放靠下就拍不到 band。

### Key Lessons

1. **「门绿」与「文档对」是两回事,而中间那层没人守。** `REG-02` 的门验算术(比值 ≥ 阈值),而 PAIR 的**地面归属**只写在散文里 ⇒ 两个地面同值时比值不变、门全绿、散文已经失真。**算术判据无法发现归属漂移**;凡「这条记录描述的对象是否还存在」这类问题,都需要一条能自动发现漂移的判据,或至少在改动时把该族**全量**过一遍。
2. **同形缺陷第三次出现:改值的时候,同族的散文与诊断串会留在原地。** v1.15 是「同一令牌画在自身底色上」重现;v1.16 是「改了值/删了令牌,而描述它的散文与读数没跟上」(三处)。**症状不同,成因同类:改动只发生在被点的那些行上,而同族的说明文字不在任何门的判据里。**
3. **断言数量不是覆盖率。** c2 19 + c4 39 里有相当一部分是对同一缺陷的重复断言 ⇒ 58 这个数字读起来像独立覆盖,实际互异覆盖更低。**多实例交付物要逐实例设门,但同一实例不要在多条路径重复设门** —— 重复会同时制造「看起来很全」与「同一条缺陷报两次」两种失真。
4. **成本论证的前提会过期。** 编排器「改 `check-05` 会作废 7 份覆盖者」的结论曾是对的,但当那 7 份因归档全部 fail-closed stale 之后,结论就失效了。**执行器实测核盘的职责不是形式,而是防止一个过期前提冻结一整条正确路线。**
5. **「先复现退化,再修」比「判断它可能退化,去修」可靠。** `check-05` 那条断言的静默死亡是先实测证明出来的(`expected=<UNRESOLVED>`,BLOCKED 2 → 3,退出码不动),而不是推断出来的。**推断出来的缺陷容易被修在错的地方** —— 修完之后 diff 看起来是对的,而缺陷仍在。
6. **纯 CSS 的里程碑,耗时大头仍不在写 CSS,而在证明没坏。** 本里程碑 67 次提交里,真正改产品面的只有很小一部分;其余是门复跑、变异、取证、重验。

### Top Lessons (Verified Across Milestones)

1. **门通过 ≠ 语义成立。** v1.13 由 D-P3-16 的决策覆盖 gate 报 30/30 而运行时是无界自动链证明;v1.14 由 `check-05 --item 9` 正面断言回归前提证明。两个里程碑独立复现同一类缺陷。
2. **不能失败的门比没有门更糟。** v1.14 新增:门必须用变异证明自己会红,否则视为未交付。v1.13 的「文本级 gate 必须配行为验证」是同一结论的弱形式。
3. **结构化文件由后端写,AI 只产内容。** v1.13 建立(annotations 字段、`AUTHORIZATION.md`、`DESIGN.md` 改名),v1.14 未出现反例。
4. **锁定模块只做末尾追加式演进。** v1.13 建立(grammar.py 末尾追加);v1.14 的对应形态是 `style.css` 的「追加,不重排」——等特异性规则由源码顺序决定,重排即渲染变更。
5. **单阶段验证看不到跨阶段回归。** v1.14 新增:错误可能不在任何一处改动里,而在两处正确改动的**组合**里;收口前的独立集成审计是唯一能看见它的位置。
6. **下游记账文件不该进 `covered_files`。** v1.14 新增:覆盖清单的语义是「其变更足以使本报告结论失效的输入」,每次收口都会变的记账文件不满足该语义,收进去会让收口动作自我打脸。
7. **门的判据粒度必须写下来:它回答什么、不回答什么。** v1.15 新增:`check-10` 的 58/58 PASS 与 G1 的构图崩塌**完全相容**——它从设计上回答「`th` 是不是画了 `--color-surface`」,从不回答「表头读起来是不是一条 band」。这是第 1 条(门通过 ≠ 语义成立)的**新形态**:前几次是门**没在看**(漏掉回归、断言了回归的前提),这次是门**看的地方对、问的问题窄**。新门交付时应显式声明它不覆盖的那一面。
8. **同形缺陷修一次不够,要留下可复用的判据。** v1.15 新增:G1 是「同一令牌画在自身底色上」的第二次出现(第一次是 v1.14 收口前为 `#doc-panel-header` 修的),相隔仅一个阶段。点修只解决实例,不解决形态;凡「某元素的自身底色与它内部某物的底色相撞」这类缺陷,应沉淀成一条可查的判据而不是一次补丁。
9. **「门绿」与「文档对」之间有一层没人守的空隙。** v1.16 新增:PAIR 的门验的是**算术**(比值 ≥ 阈值),而它的**地面归属**只写在散文里 ⇒ 两个地面同值时比值不变、门全绿、散文已经失真。**算术判据无法发现归属漂移。** 凡「这条记录描述的对象是否还存在」这类问题,都需要一条能自动发现漂移的判据,或在改动时把该族**全量**过一遍 —— 否则改动的实际影响面会大于门的覆盖面。
10. **断言数量不是覆盖率。** v1.16 新增:同一条缺陷可以在多条路径被重复设门(对 `#doc-panel` 的同样三条断言写在 c2 与 c4 两处),于是计数看起来像独立覆盖,实际互异覆盖更低,且同一条缺陷会报两次。**多实例交付物要逐实例设门,但同一实例不要在多路径重复设门。**
11. **成本论证的前提会过期。** v1.16 新增:编排器「改 `check-05` 会作废 7 份覆盖者」曾是对的,但那 7 份因归档全部 fail-closed stale 之后结论即失效。**执行器实测核盘的职责是防止一个过期前提冻结一整条正确路线**,不是形式。
12. **「先复现退化,再修」比「判断它可能退化,去修」可靠。** v1.16 新增:`check-05` 那条断言的静默死亡是先实测证明出来的(`expected=<UNRESOLVED>`,BLOCKED 2 → 3、退出码不动),不是推断出来的。**推断出来的缺陷容易被修在错的地方** —— 修完之后 diff 看起来是对的,而缺陷仍在。
