# Project Retrospective

*A living document updated after each milestone. Lessons feed forward into future planning.*

## Milestone: v1.13 — 交互式讨论迭代系统 MVP

**Shipped:** 2026-09-13
**Phases:** 3 | **Plans:** 13 | **Tasks:** 28

### What Was Built

- **行走骨架(Phase 1)**:FastAPI 服务器 + 单界面;双轨 AICaller(SDK / `claude -p --output-format stream-json`)界面契约一致;SSE 事件直播(说/读/写/命令/结果/错误/完成七种 kind)+ 中止;`derive_state()` §7.4 八行推导表(文件即状态);阶段 1-2 连续会话与 transcript 恢复;发散模式;G1 定稿为 `discuss-round-1.md`。
- **轮次收敛循环(Phase 2)**:划词批注与大白话即时答双轨;批注回应表回写 `answer`/`status`(AI 不碰 JSON);轮次冻结只读;`grammar.py` §6.4 六条文法解析器 + 正反例测试矩阵。
- **授权、自检与终点(Phase 3)**:G3 四处机械校验 + 确认词 + 后端写 `AUTHORIZATION.md`;`DESIGN.md.tmp` 原子落盘;宽松/严格两档自检、核查者/修复者双角色自动循环;D-22 残余裁决制(纯 P2 轮转用户逐条裁决);崩溃自愈;使命完成只读归档。

**规模:** 155 commits,2026-09-08 → 2026-09-13;13,322 LOC(不含 vendor);15 个测试文件,219 passed / 6 skipped(慢速真 CLI E2E 由 `IDI_E2E=1` 门控)。

### What Worked

- **纵向 MVP 切阶段**:P1 骨架 → P2 收敛循环 → P3 门与终点,每阶段结束都能用真实目录跑通一段端到端流程,验证永远有真实对象可用。
- **真浏览器 UAT(原始 CDP)**:三个阶段的 UAT 共抓出 6 处机器级验证与静态读码都漏掉的真实缺陷,包括一处高危的无界自动链(实测 84 跳/1.5s)。这是本项目最有性价比的验证手段。
- **验证器 + 缺口修复 + 原验证器复验的闭环**:`gaps_found` → 独立复现确认 → 修复分支 → 原验证器复验 → 翻状态,三次(Phase 1/2/3)全部一次收敛。
- **指纹漂移的诚实处理**:Phase 1 与里程碑收口的 Phase 1/2 `covered_digest` 漂移,一律以重新验证刷新指纹收口,而非覆盖状态字段。

### What Was Inefficient

- **plan-checker 三轮迭代**:Phase 3 计划经 3 轮才通过(3B+5W+2I → 1B+3W+1I → PASS),其中多条(如 `AuthorizeBody` 空体 422 陷阱、路由交付权归属)本可在计划阶段一次说清。
- **STATE.md 在 `phase.complete` 后出现字段异常**(`completed_phases: 1`、By-Phase 表重复、进度条 0%),需人工修正——工具侧的状态写入与派生视图未完全对齐。
- **CLI 耗尽窗口**:真实 CLI 调用偶发停滞 20+ 分钟零事件,只能中止重试,期间无法区分"慢"与"死"。
- **用户全局 `settings.json` 的 allow 规则**一度绕过 §5.4 权限门,直到实测才暴露——环境依赖类风险靠读码发现不了。

### Patterns Established

- **两路线必须 `setting_sources=[]`(SDK)/`--setting-sources=`(CLI)**:屏蔽全局 allow 规则,权限矩阵才成立。
- **AI 不写结构化文件**:annotations 字段、`AUTHORIZATION.md`、`DESIGN.md` 改名全由后端执行,AI 只产出内容,格式漂移归零。
- **纯模块 + 薄路由**:`grammar.py`/`annotations.py`/`g3.py`/`checks.py` 无 I/O 依赖、可独立测;路由只做接线与 409 分流。
- **锁定模块的增量演进**:Phase 3 新增解析器只在 `grammar.py` 文件末尾追加,Phase 2 的六个解析器与 `_VERDICT_RE` 字节不变。
- **缺口修复只碰必要文件**:G-idi03-1~4 全部修复仅 3 个文件(session.py/app.js/测试),grammar/state/checks/g3/main/prompts 零改动。

### Key Lessons

1. **门通过 ≠ 语义成立。** D-P3-16 的决策覆盖 gate 报 30/30(它只扫 PLAN/SUMMARY 文本),而同一条决策在运行时是活偏差(G-idi03-1 无界自动链)。任何"文本级 gate"必须配行为验证佐证。
2. **文件即状态的推论要推到边界。** "冻结 = 纯磁盘推导(轮号 < current_round)"和"半成品报告重跑覆盖"这类推论,一旦落到实现就省掉整个状态机——但推论必须在计划期显式写出,否则实现者会各自发明。
3. **锚点与配对空间必须单一口径。** 裁决行的"结论行取末一处"锚点若与展示层的扫描口径不一致(G-idi03-2),界面就会静默隐藏用户必须看到的问题。
4. **预算纪律前置**:单跳调用必须有明确的 hop 上界,否则 `finally` 守卫写反就是无界循环。
5. **Prompt 契约要测**:"函数接受了参数"不等于"参数进了 prompt"(`build_check_prompt` 的 tier 注入缺陷靠真 E2E 才抓到)。

### Cost Observations

- Model mix: 编排器与执行器以 sonnet 为主,验证/审计类子代理用 sonnet 或 opus(按任务深度)
- Sessions: 跨多个会话,期间遭遇 503/429/ENOTFOUND 与 600s 流看门狗停滞,均以恢复或重启代理收敛
- Notable: 真 CLI E2E 是耗时大头(单次真实调用数分钟起),但正是它抓到了 prompt 注入缺陷;慢速测试用 `IDI_E2E=1` 门控,日常套件保持秒级

## Milestone: v1.14 — 前端视觉与可访问性

**Shipped:** 2026-09-26(范围收口 2026-09-24,归档 2026-09-26)
**Phases:** 6 | **Plans:** 21 | **Tasks:** 60

### What Was Built

- **设计契约与令牌层(Phase 4 + 4.1)**:`style.css` 顶部单一围栏 `:root` 令牌块(8 档字号 / 5 条行高 / 4 个 `z-index` / 25 个 Radix primitive / 47 个 `--color-*`),全部字面量替换为 `var()`,围栏外裸 hex 由 117 归 0;四条零依赖契约校验命令(`check-01`…`check-04`),每条失败方向经变异证明。颜色族由手调 hex 换成 Radix Colors 12 步语义刻度。
- **排版与视觉层级(Phase 5)**:不可逆的 G3 授权按钮在**形态**上与五只例行/承诺按钮分离(淡底 vs 实心 vs 实心更深,四个强调通道用满);页面级层级链 28 > 24 > 22 > 14 由运行时断言钉死;`renderMarkdown()` 全部 9 个注入目标的标题刻度受控(UA 默认与第四字重档 700 退出应用);侧栏活动面板由纯 CSS 推导标出;两处写死 emoji 换成跟随令牌的掩码字形。
- **布局稳健性(Phase 6)**:`#state-badge` 魔法数消除、窄窗口不破版、滚动容器套娃收敛、紧凑控件 24×24 命中区。LAYOUT-02 的 768px 承诺按实测收窄为「badge 不被横幅遮挡」并登记 A-10。
- **交互状态与焦点(Phase 7)**:全站作者化 `:focus-visible`(七选择器 + 三条 PAIR)、hover/active/disabled 三态覆盖(禁用态**未被软化**)、过渡限定两个属性 120ms + `prefers-reduced-motion`。
- **可访问性语义与键盘(Phase 8)**:`#round-doc` 的 Tab 停靠点让 Phase 7 预埋的焦点环第一次真正生效;Shift 释放手势把键盘文本选区接成可用的批注路径;两个阻塞弹窗宣告 `role="dialog"` + `aria-modal` 并由原生 `inert` 让该宣告成真,单点 Escape 分派器;`b9664e0` 五条修复的六项人工验收全量重跑。
- **收口期(quick `260925-iin` + 预收口审计)**:修复一处跨阶段回归,新增两条门,处置 backlog `999.1` 的两项,并让六个阶段的指纹全部重新验证通过。

**规模:** 296 commits,2026-09-17 → 2026-09-26;产品面 23 文件 +8490 / −401;前端 3,831 LOC(`style.css` 1708 / `app.js` 1854 / `index.html` 269);后端零改动(219 passed / 6 skipped)。

### What Worked

- **预收口审计真的抓到了东西。** `/gsd-audit-milestone` 的跨阶段集成检查发现 Phase 6 的 L-4 静默杀掉了 AI 事件自动跟随——这是一个**零覆盖**的真实回归,而且没有任何单阶段验证会看到它(它跨两个阶段:改 CSS 的阶段与写 `scrollTop` 的阶段)。里程碑收口前的这次独立审计是本里程碑性价比最高的一步。
- **变异测试作为门的验收标准。** 本里程碑反复出现「门绿但没在看」的缺陷,而**唯一**能证明一条门真的会失败的手段是把被测行为破坏掉、看它变红。FIX 2 的自动跟随门与 FIX 5 的枚举对齐门都按这个标准交付,并留下了逐字的变异输出。
- **「先怀疑自己的探针」。** 两次假警报(把 999.2 的前提误判为陈旧、把 SUMMARY 的 `status` 误判为缺失)都由逐字复测原命令澄清,而不是靠推理。第二次尤其:差一点就让一条真实缺口被「订正」掉。
- **用户裁定与执行分离。** 20px 字面量的处置(加档 / 重映射 / 加例外)是一个真正的排版决策,不是机械替换——把它交回用户、并锁定修法形状后再执行,避免了执行器自行发明第三种修法。
- **指纹作废的诚实处理。** 本次修复让 6 个阶段的指纹全部失效。处置是**逐份以 HEAD 内容重新验证**,而不是刷新旧指纹——刷新等于断言「自验证以来什么都没变」,而这里恰好是假的。

### What Was Inefficient

- **`check-05 --item 9` 的存在本身就是一次浪费。** 它不但没覆盖自动跟随,还正面断言了回归的前提(`#ai-events 计算 max-height == none`)。一条断言了错误不变量的门比没有门更糟:它会让后来者以为这块已被守住。教训是「门要断言**性质**,不是断言**当前实现的形态**」。
- **`covered_files` 的记账语义没有早点想清。** `REQUIREMENTS.md` 出现在全部 6 份报告里,而 `phase.complete` 每次收口都会改它——收口动作本身会打掉所有报告。这个问题在 Phase 4 就被记下并建议移出,直到收口前才真正执行。**下游记账文件不该进 `covered_files`。**
- **`phase.complete` 的进度计数器第四次复现异常**(`completed_phases` / `percent` 被往回改)。已注册的 tech-debt,不自愈,每次收口都要编排器自己核盘。
- **门标签宽于实测四处。** L-5「每个」实为 9/10 行、L-6 只测可见行、SC4 用固定 12 次 Tab 窗口、`check-07` g1 措辞不符。都不影响已通过的结论,但门文本与真实覆盖面不一致。
- **plan-checker 抓到了编排器自己引入的矛盾。** Task 4 的反对空转前提「恰好 7 项」与 `<done>` 的「变异 B → FAIL」互斥。这次是好的低效。

### Patterns Established

- **一条门必须能失败,并且要用变异证明。** 交付门时附上「把被测行为破坏掉后它变红」的逐字输出,否则该门视为未交付。
- **门断言性质,不断言实现形态。** 「自动跟随」的性质是「新条目落在可视盒内且**门自己不动滚动位置**」;写成「`max-height == none`」就变成了对当前实现的快照,实现一改门就撒谎。
- **枚举式规则的两侧必须逐字同集,并在两侧都写明。** `FOCUSABLE_SELECTOR`(门)与 `:focus-visible` 的七选择器(CSS)必须同一次改完;只改一侧会让「规则覆盖了谁」与「门检查了谁」重新分叉,而门会绿。
- **反事实探针与常驻门分工。** 门承担可重复的算术断言;探针承担「这条断言有没有服务对象、它的算术在真实渲染值上成不成立」。
- **追加,不重排。** `style.css` 至少一对等特异性规则由源码顺序决定;重排即渲染变更而 diff 看起来完全无辜。本里程碑全程守住。
- **指纹失效后重新验证,不刷新。** 内容真变 → 重新验证;记账性编辑 → 重算指纹并在报告内披露改了什么。判据是拿 HEAD 内容重算比对,不是看 mtime。

### Key Lessons

1. **单阶段验证看不到跨阶段回归。** L-4 的改动在 Phase 6 完全正确(它的门全绿),`scrollTop` 的代码在 Phase 2 完全正确;错的是两者的**组合**。收口前的独立集成审计是唯一能看见它的位置。
2. **不能失败的门比没有门更糟。** 它不只是漏掉缺陷,还会让缺陷**看起来已被守住**。任何新门都必须先回答「我把它防的那个行为破坏掉,它会红吗」。
3. **下游记账文件不该进 `covered_files`。** 覆盖清单的语义是「其变更足以使本报告结论失效的输入」;需求索引表、状态归一这类每次收口都会变的记账文件不满足该语义,收进去就会让收口动作自我打脸。
4. **子代理的自述不可信,要复测原命令。** 两次假警报都源于「读到了输出,但没读它**怎么产生**的」——item 9 输出里的 `<summary>` 是它自己造的,`SUMMARY.md` 的 `status` 在第 114 行而我只看了前 60 行。
5. **加档优于重映射,当交付物的视觉是已签核的。** 20px → `--text-lg-plus` 保持字形渲染尺寸不变;重映射会改已出货的 ▾/▸ 视觉,加例外则让裸字面量永久留在出货 chrome 里。代价是命名阶梯非单调(xl=24 > 2xl=22),已作为 D-07 冲突登记。

### Cost Observations

- Model mix: 编排器与执行器以 sonnet 为主;验证/审计类子代理用 sonnet 或 opus(按任务深度)
- Sessions: 跨多个会话;本里程碑末期遭遇一次上下文压缩,收口在压缩后继续
- Notable: 真浏览器 UAT(`check-05` 十项 + 两个一次性探针)是耗时大头,但也是唯一能抓到运行时语义缺陷的手段;`check-05` 全量跑 exit=2 是 item 5 两条 `--ai-smoke` 腿按设计 BLOCKED,不是回归

### Top Lessons (Verified Across Milestones)

1. **门通过 ≠ 语义成立。** v1.13 由 D-P3-16 的决策覆盖 gate 报 30/30 而运行时是无界自动链证明;v1.14 由 `check-05 --item 9` 正面断言回归前提证明。两个里程碑独立复现同一类缺陷。
2. **不能失败的门比没有门更糟。** v1.14 新增:门必须用变异证明自己会红,否则视为未交付。v1.13 的「文本级 gate 必须配行为验证」是同一结论的弱形式。
3. **结构化文件由后端写,AI 只产内容。** v1.13 建立(annotations 字段、`AUTHORIZATION.md`、`DESIGN.md` 改名),v1.14 未出现反例。
4. **锁定模块只做末尾追加式演进。** v1.13 建立(grammar.py 末尾追加);v1.14 的对应形态是 `style.css` 的「追加,不重排」——等特异性规则由源码顺序决定,重排即渲染变更。
5. **单阶段验证看不到跨阶段回归。** v1.14 新增:错误可能不在任何一处改动里,而在两处正确改动的**组合**里;收口前的独立集成审计是唯一能看见它的位置。
6. **下游记账文件不该进 `covered_files`。** v1.14 新增:覆盖清单的语义是「其变更足以使本报告结论失效的输入」,每次收口都会变的记账文件不满足该语义,收进去会让收口动作自我打脸。
